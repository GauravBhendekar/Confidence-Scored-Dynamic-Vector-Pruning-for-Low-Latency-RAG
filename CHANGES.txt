SECTION 0 — TL;DR / QUICK REFERENCE
===============================================================================

WHAT WAS BROKEN
  1. Tier 3 (complex) queries retrieved PARENT BLOCKS (~700 tok each) while the
     baseline retrieved STANDARD chunks (~200 tok each). Result: complex queries
     used MORE tokens than baseline -> NEGATIVE savings (-162% to -197%).
     Mean savings across the benchmark was -39.5%.

  2. No LLM was ever running. The provider silently fell back to a keyword
     extraction stub, producing a bogus identical ~4,150 ms latency for both
     pipelines. Answer quality could not be measured at all.

  3. The first benchmark query absorbed ~62 s of model cold-start, inflating
     baseline mean latency from ~4,900 ms to a false 14,012 ms.

  4. Duplicate chunks: every paragraph is indexed at 3 granularities, so the
     same text could occupy 2 of the 5 retained slots.

  5. Flat score curves on complex (multi-hop) queries were clamped to min_k,
     silently dropping needed facts.

WHAT WAS FIXED
  Fix 1  Tier 3 now retrieves STANDARD granularity; max_k capped at 5 (baseline k).
  Fix 2  LLM provider rewritten: GGUF -> Ollama -> extractive fallback, with
         honest backend reporting and warm_up().
  Fix 3  Benchmark calls warm_up() before measuring; records llm_status.
  Fix 4  Added _dedupe_by_text() in the QATM pipeline after retrieval.
  Fix 5  Pruner detects flat distributions for Tier 3 and widens to max_k.

RESULT (verified with llama3.2 via Ollama, 6 queries, warmed up)
  Metric                    Baseline (k=5)    QATM-RAG      Change
  Mean context tokens       289.83            232.0         -20.5%
  Median context tokens     292.5             218.0         -25.4%
  P95 context tokens        352.25            352.25        0%
  Mean total latency        4,064 ms          3,744 ms      -7.9%
  P95 total latency         5,276 ms          5,387 ms      +2.1%
  Avg retained chunks       5.0               4.0           -1

SECTION 5 — TROUBLESHOOTING
===============================================================================

SYMPTOM: Benchmark says "Operating in deterministic extractive fallback mode"
CAUSE  : Ollama not reachable, or model not pulled.
FIX    : Start Ollama. Run `ollama list`. If empty: `ollama pull llama3.2`.
         Check the host/port in configs/default_config.yaml (llm.ollama_host).

SYMPTOM: Benchmark says "Ollama is reachable but model 'X' is not pulled"
CAUSE  : Config model name != installed model name.
FIX    : `ollama list` to see exact names, then set llm.ollama_model to match.
         (Matching ignores the ":latest" suffix automatically.)

SYMPTOM: First query takes 60+ seconds
CAUSE  : Model cold-start (loading weights into memory).
FIX    : Already handled — warm_up() runs before measurement. If it still
         skews, confirm summary.llm_status.warmed_up == true.

SYMPTOM: PowerShell reports exit code 1 but the report was written
CAUSE  : Embedding model progress bar on stderr.
FIX    : Cosmetic. Ignore, or redirect with 2>$null.

SYMPTOM: Token savings are negative again
CAUSE  : Tier 3 granularity reverted to PARENT_BLOCK, or max_k raised above 5.
FIX    : In qatm_pipeline.py, Tier 3 must use Granularity.STANDARD.
         In gradient_pruner.py, Tier 3 max_k must be 5, not 6.

SYMPTOM: /api/query returns "Information not found in context." for BOTH pipelines
CAUSE  : NOT a bug. The question is not answerable from the indexed document.
         Observed on q6 — both baseline and QATM fail identically because the
         source doc does not explain the asked relationship.
FIX    : Use a corpus that actually contains the answer.

SYMPTOM: uvicorn exits immediately with no output
CAUSE  : Possibly port 8000 already in use.
FIX    : Try another port: --port 8001. Check with:
         Test-NetConnection -ComputerName 127.0.0.1 -Port 8000

SECTION 6 — KNOWN CAVEATS BEFORE PUBLISHING (READ THIS)
===============================================================================

  1. THE EVAL SET IS TINY. 6 queries on 1 document. This cannot support a
     publication claim. Needed: HotpotQA / SQuAD / MS-MARCO subsets.

  2. LATENCY SIGNAL IS WEAK. Mean latency improved only -7.9%, and P95 was
     slightly WORSE (+2.1%). With 6 short queries the difference is within
     noise. Token savings (-20.5%) are the consistent, defensible result.

  3. NO ANSWER-QUALITY METRIC EXISTS. The framework measures COST only
     (tokens, latency, depth). It does NOT measure whether accuracy is
     preserved. Ragas is mentioned in docs but is NOT implemented and NOT in
     requirements.txt. Until faithfulness / EM / F1 exists, results should be
     reported as cost reductions only, NOT as "no accuracy loss".

  4. THE INDEXED DOCUMENT IS THE PROJECT'S OWN PROPOSAL. It contains the paper's
     EXPECTED results table, so generated answers can quote those expected
     figures as if they were findings (this happens on q5). Use a NEUTRAL corpus
     for final measurements.

  5. ONLY TESTED ON CPU EMBEDDINGS. configs/default_config.yaml says
     device: "cuda" but the entry points hardcode device="cpu".

  6. API SOURCE REPORTING IS COSMETIC-ONLY BUG. In app/main.py, the retrieved
     chunk "text" field returns the document NAME rather than the chunk text
     (the dict comprehension reuses variable "s" for both the state object and
     the source dict). Fix before any demo of the dashboard.
